# [Plan] The dashboard on Windows without WSL

What to change so the dashboard, the runner, the drivers and the scheduler run on Windows itself, and how to check it with no Windows machine at hand.

## Problems

1. **No Windows to try it on.** An agent here works on macOS; the only Windows it can reach is a GitHub `windows-latest` runner. So "check that it works" is a CI job that builds, runs the tests, starts the dashboard and runs a scripted agent (the `pnpm demo` flow, `packages/dashboard/src/e2e/README.md`), not a person clicking. A run on the real Claude Code and Codex needs logins a runner does not have: that last check is a person's, after this work.
2. **Stopping a run gracefully.** The Stop button (`dashboard/src/dashboard-rpc/control.ts:58`) sends `SIGINT` to the runner, and the scheduler stops its process the same way (`skill-scheduler/src/scheduler.ts:262`). On Windows `process.kill(pid, 'SIGINT')` terminates the process outright: no handler runs, so the run never ends its turn, writes its card or pushes. This is the one change that needs a design, not a substitution.
3. **Agent CLIs installed by npm are `.cmd` shims.** `spawn('claude')` / `spawn('codex')` (`agent-driver/claude/src/claude-code.ts`, `claude-code-models.ts`, `claude-code-quota.ts`, `agent-driver/codex/src/codex.ts`, `codex-ask.ts`, `agent-driver/core/src/ready.ts` probe) fail with ENOENT for `claude.cmd`, and Node refuses to spawn a `.cmd` without a shell (EINVAL since the 2024 fix). The native installers give `claude.exe` / `codex.exe`, which work.

## Solutions

1. CI: add a `windows` job to `.github/workflows/ci.yml` (`runs-on: windows-latest`): `pnpm install`, `pnpm build`, the tests of `agent-driver`, `agent-runner`, `agent-data`, `dashboard`, `skill-scheduler`, `skill-queue`, `skill-tickets`, `skill-branches`, then the dashboard's e2e with the scripted agent. Start it non-blocking (`continue-on-error`) while the fixes land, make it required once green. Tests that assume POSIX (paths with `/`, `sh` fixtures, file modes) get fixed or, when the feature is POSIX-only (servers over ssh, `install` mac/linux), skipped on win32 with a reason.
2. Stop: one helper `askToStop(pid)` in `agent-data` (shared by dashboard and scheduler). POSIX: `SIGINT` as today. Windows: write a stop file next to the run's card (`<run>.stop`) that the runner watches (`fs.watch` plus a poll); the runner treats it exactly as its `SIGINT` handler (`agent-runner/src/run.ts:528`). Alternatives weighed: an IPC channel (gone once the dashboard restarts, the runner is detached), `GenerateConsoleCtrlEvent` (no Node API, needs a shared console). The file is the only one that survives a dashboard restart; use it on every platform if it proves simpler, dropping the signal path (no backwards compatibility needed).
3. `.cmd` shims: one `resolveBin(name)` in `agent-driver/core`: on win32 search `PATH` × `PATHEXT` (as `dashboard/src/dashboard/open-in-app.ts:46` already does: move that code there and reuse it); an `.exe` spawns as is; a `.cmd`/`.bat` npm shim is read for the `node_modules/.../cli.js` it runs and spawned as `process.execPath <that file>`, so no shell quoting of the prompt is ever needed (a prompt through `cmd.exe` is an injection risk and breaks on `%`, `^`, `"`). Every driver spawn and the readiness probe go through it.

## Implementation

Each step a commit, each with its unit tests (pass `platform` in, as `cli/browser.ts` and `pick-directory.ts` already do, so macOS CI tests the win32 branch too).

1. **Home folder.** Replace `env.HOME ?? ''` / `env['HOME'] ?? homedir()` with `homedir()` (it reads `HOME` first on POSIX and `USERPROFILE` on Windows, so tests setting `HOME` keep working on POSIX; on Windows tests set `USERPROFILE` too). Sites: `dashboard/src/registry.ts:335`, `secure-address.ts:27`, `local-bin.ts:11`, `pick-directory.ts:118`, `dashboard/logins-sync.ts:131,272`, `dashboard-devices/src/home-file.ts:16`, `agent-data/src/personal-folder.ts:24`, `sessions.ts:18`, `skill-account-rotation/src/files.ts:10`, `wiring.ts:60`, `agent-driver/claude/src/claude-code.ts:208`, `claude-accounts.ts:35`, `agent-driver/codex/src/codex-home.ts:11,21`, `skill-github/src/accounts.ts:46,131`. The `''` fallbacks are a bug on any platform (a relative `.openagent-address` in the cwd).
2. **A shell line.** One `shellLine(line): [command, args]` in `agent-data`: POSIX `['sh', ['-c', line]]`, win32 `['cmd.exe', ['/d', '/s', '/c', line]]` with `windowsVerbatimArguments: true`. Users: `dashboard/src/project-hooks.ts:338`, `agent-runner/src/ended.ts:106`, `dashboard/src/dashboard-rpc/logins.ts:304`, `skill-scheduler/src/check.ts:27`, `skill-orchestration/src/check.ts:39`. These lines are written by the project (hooks, checks, ended-run lines) and today are POSIX shell: say in the docs of each that on Windows they run in `cmd`; when a check is shipped by a skill (`ai-skills` SKILL.md `check:` lines), make it `npx …` only, which both shells run alike. `skill-github/src/job.ts:69` is a whole `sh` script: rewrite it as a node child (`process.execPath` with a small script that runs the job, writes the log and exit file) so it needs no shell at all.
3. **Tree kills.** One `killTree(pid, signal)` (already in `agent-driver/core/src/child-registry.ts:25`; move it to `agent-data` or export it and reuse): POSIX `process.kill(-pid)`, win32 `spawnSync('taskkill', ['/T', '/F', '/PID', pid])`. Users: `child-registry.ts`, `agent-runner/src/ended.ts:110`, `dashboard-rpc/logins.ts:295`, `claude-login.ts:209`, `dashboard-devices/src/door/cli.ts:423`, `skill-github/src/job.ts:81`.
4. **No console windows.** Every `detached: true` spawn on Windows opens a console window: add `windowsHide: true` to all of them (`agent-runner/src/runner.ts:162`, `agent-driver/core/src/cli-session.ts:172`, `dashboard/src/package-services.ts:53`, `skill-scheduler/src/scheduler.ts:177`, `skill-github/src/merge-watch.ts:129`, `skill-browser/src/cli.ts:170`, `skill-account-rotation/src/adding.ts:72`, `dashboard-devices/src/door/persons.ts:12`, `servers/cli.ts:257`), and to the hook/check spawns of step 2.
5. **Agent binaries** (Solution 3).
6. **Stop** (Solution 2), dashboard Stop button and `scheduler stop` both.
7. **Logins.** `agent-driver/claude/src/claude-login.ts:188-191` lends a terminal with `script` and `stty`, which Windows lacks. On win32 run `claude setup-token`/login through `node-pty`-free means: spawn the resolved binary directly with piped stdio and the URL scraped from its output; if Claude Code refuses without a TTY, show the person the command to run in their own terminal instead (the button's text already shows the command line, `ready.ts:26`). Same check for Codex's login (`codex-accounts.ts:215` already opens the browser on win32).
8. **Skill links.** `dashboard/src/project-skills/apply.ts:48` makes a real directory symlink on purpose (git tracks a link, not a junction); on Windows it fails without Developer Mode and the skill is then left out with a reason. Keep it, but make the reason say "turn on Developer Mode in Windows settings" on win32, and set `core.symlinks=true` on clones (`dashboard/src/clone-project.ts`) so a checkout of a project with links gets links, not text files. `skill-branches` already uses junctions for its own links.
9. **CI job** (Solution 1), then fix what it shows: likely string paths split on `/` (search `split('/')`, `.startsWith(root + '/')`, `'/'` joins of filesystem paths), file modes asserted in tests (`chmod` is a no-op on Windows: skip those assertions on win32), and `health.ts` (linux/darwin only: give win32 a branch or none).
10. Hand-over: note in the ticket for a person to try a real Claude Code and a real Codex run on Windows; then `tickets/2026-11-10_install-on-windows.md` can build on it.

## Considerations

- Out of scope, POSIX by nature: `install` (mac/linux services), `dashboard-devices` servers (ssh to Linux), `pfctl`/`ifconfig`. They must fail with a clear "not on Windows" rather than a spawn error; nothing more.
- `git` on Windows: `core.autocrlf=true` (Git for Windows' default) turns ticket and queue files into CRLF; the `agent-data` branch writes go through `git` plumbing and read back with `\r\n`. Parsers of tickets, plans, queue and SKILL.md front matter must accept `\r\n` (check `skill-queue/src/queue.ts`, `skill-tickets`, `skill-scheduler/src/automation-file.ts`), or set `core.autocrlf=false` in the worktrees OpenAgent creates.
- Path length: `.branches/agent-<iso>/node_modules/...` easily passes 260 characters; `git config core.longpaths true` on the worktrees, and Node itself handles long paths.
- `process.kill(pid, 0)` for liveness (`isPidAlive`) works on Windows; pid reuse is faster there, which the cards' `host`+`pid` checks already tolerate.
- The prompt goes to the agent as an argument: through `resolveBin` no shell sees it; a Windows command line is capped at 32 767 characters, so a long prompt (a whole ticket plus check output) should go on stdin where the CLI takes it (Claude Code `-p` reads stdin).
